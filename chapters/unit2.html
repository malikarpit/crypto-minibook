2.1 Diffie-Hellman Key Exchange

📚 Prerequisite
Modular exponentiation from Unit 1 Section 1.0. Recall: computing gˣ mod p is easy; finding x given gˣ mod p is hard (Discrete Logarithm Problem).
Diffie-Hellman Key Exchange (Diffie & Hellman, 1976)
Solves the fundamental problem: how do two parties agree on a secret key over an insecure public channel without ever transmitting the key? Security is based on the computational hardness of the Discrete Logarithm Problem (DLP).

Protocol Steps

  1. Public agreement: Alice and Bob publicly agree on a large prime p and a generator g (a primitive root modulo p). These are public knowledge — Eve knows them too.
  2. Private choices: Alice chooses a secret integer a. Bob chooses a secret integer b. These are NEVER shared.
  3. Public values: Alice computes A = gᵃ mod p and sends A to Bob. Bob computes B = gᵇ mod p and sends B to Alice.
  4. Shared secret: Alice computes S = Bᵃ mod p. Bob computes S = Aᵇ mod p. They get the same secret!
Why the shared secrets match
Alice: S = Bᵃ mod p = (gᵇ)ᵃ mod p = gᵃᵇ mod p
Bob: S = Aᵇ mod p = (gᵃ)ᵇ mod p = gᵃᵇ mod p
Both = gᵃᵇ mod p ✓

Eve sees: p, g, A, B — but must solve A = gᵃ mod p for a. This is the DLP. Infeasible for large p.
Numerical Example (small values for illustration)
Public: p = 23, g = 5 Alice: a = 6, A = 5⁶ mod 23 = 15625 mod 23 = 8 Bob: b = 15, B = 5¹⁵ mod 23 = ... = 19 Alice sends A=8 to Bob, Bob sends B=19 to Alice. Alice: S = 19⁶ mod 23 = 47045881 mod 23 = 2 Bob: S = 8¹⁵ mod 23 = ... = 2 Shared Secret = 2 ✓ (Eve only knows 23, 5, 8, 19 — cannot find 2)
⚠️
DH is unauthenticated! Pure DH has no way to verify WHO you are talking to. Eve can intercept, establish separate DH sessions with both Alice and Bob, and relay messages. This is the Man-in-the-Middle (MitM) attack — covered in Section 2.5. DH is always combined with digital signatures in practice (e.g., in TLS, the server signs its DH parameters with its RSA/ECDSA certificate).
⚡ Extra: DH Parameter Sizes & Logjam Attack

For DH, the prime p must be large: at least 2048 bits for modern security (analogous to RSA). In 2015, researchers discovered the Logjam attack: many servers were configured to use 512-bit or 768-bit "export-grade" DH primes — small enough that governments (and well-funded attackers) precomputed discrete logarithms for the most common primes. A server and client could be coerced into "downgrading" to weak DH. Fix: use 2048-bit+ primes, or better, switch to ECDH (Section 2.2) which is both more secure and faster.

🔬 Advanced: Index Calculus — Breaking DLP

The best classical algorithm for solving DLP over multiplicative groups is the Index Calculus method, running in sub-exponential time: Lp[1/3, c] where c ≈ 1.923. This is why DH requires primes of 2048+ bits to be secure. The Index Calculus exploits the multiplicative structure of Zp* by expressing discrete logs of unknown elements as linear combinations of logs of small “factor base” primes (a process called “sieving”). ECDLP has no analogous sub-exponential attack — hence ECC is preferred. The best known ECDLP algorithm is Pollard's rho, running in O(√n) — purely exponential in the key size.

🔬 Advanced: DDH Assumption — Formal Security Foundation of DH

DH security rests on a hierarchy of three assumptions, each strictly stronger than the next:

DH Assumption Hierarchy (hardest to solve → easiest)
DLP: Given ga mod p, find a
CDH: Given ga, gb, compute gab
DDH: Distinguish (ga, gb, gab) from (ga, gb, gc) for random c

DLP hard ⇒ CDH hard ⇒ DDH hard (NOT reversible). Most DH proofs use DDH. DDH fails over Zp* with smooth p−1 (Legendre symbol test) — hence DH primes must be safe primes (p=2q+1, q prime).

The DDH assumption is the basis for ElGamal encryption and Cramer-Shoup (first CCA2-secure scheme under a standard assumption). Over prime-order elliptic curve groups, DDH is believed to hold unconditionally — making ECDH provably secure under a weaker assumption than DLP. The hierarchy matters: breaking CDH doesn't require breaking DLP, and breaking DDH doesn't require breaking CDH.

Q1. In DH with p=23, g=5, a=6, A=8 is public. Why can Eve not compute the shared secret from p,g,A,B alone?
Eve needs to solve A = g^a mod p for a (the Discrete Logarithm Problem). For small p=23 this is trivial, but for 2048-bit primes the DLP is computationally infeasible. The best classical algorithm (Index Calculus) runs in sub-exponential time L_p[1/3, 1.923] — still requires centuries for 2048-bit primes.
Q2. What is the Logjam attack and how is it prevented?
Logjam (2015) downgraded DH to 512-bit export-grade primes by intercepting the TLS handshake. Attackers precomputed discrete logs for the most common weak primes. Prevention: use 2048-bit+ primes, or switch to ECDH (P-256 or X25519) which has no analogous sub-exponential attack.
Q3. DH is vulnerable to MitM — how do real protocols prevent this?
The server signs its DH public parameters with its long-term RSA/ECDSA certificate key. The client verifies this signature against the server's X.509 certificate. Eve cannot forge the signature without the server's private key, so even if she intercepts the DH exchange, authentication fails.
  • DH security rests on the DLP: given g^a mod p, finding a is computationally infeasible for 2048-bit primes
  • DH provides no authentication — always combined with signatures (ECDSA/RSA) in practice
  • Logjam: 512-bit export-grade DH broken by precomputation; fix = 2048-bit primes or ECDH
  • DDH assumption (stronger than DLP) is the formal security basis for ElGamal and Cramer-Shoup schemes

2.2 ECDH & Ephemeral Key Exchange

ECDH (Elliptic Curve Diffie-Hellman) is the same concept as DH but performed on an elliptic curve group instead of a multiplicative integer group. Because ECDLP is harder than DLP, ECDH achieves the same security with much smaller parameters (256-bit vs 2048-bit keys).

FeatureClassic DHECDH
Group OperationModular exponentiation (Zp*)Elliptic Curve point multiplication
Hard ProblemDiscrete Logarithm (DLP)Elliptic Curve Discrete Logarithm (ECDLP)
Key Size (128-bit security)3072 bits256 bits
PerformanceSlower~10x faster at equivalent security
Use in TLS 1.3Not recommendedMandatory (ECDHE)

Ephemeral DH / ECDHE: The “E” in ECDHE stands for Ephemeral — a brand-new key pair is generated for every single connection and deleted immediately after. This provides Perfect Forward Secrecy (covered in Section 2.7).

ECDHE Full Step-by-Step & HKDF Key Derivation

ECDHE in TLS 1.3 (Curve25519 / X25519)
Step 1: Server generates ephemeral EC key pair server_priv = random scalar s (256-bit random integer) server_pub = s × G (point on Curve25519 = 32 bytes) Step 2: Client generates ephemeral EC key pair client_priv = random scalar c client_pub = c × G Step 3: Key exchange Both send their public points (32 bytes each) in the TLS Hello messages. Step 4: Shared ECDH output Both compute: ecdh_output = c × (s × G) = s × (c × G) = cs×G Result: same 32-byte x-coordinate of the shared point Step 5: Key Derivation via HKDF (RFC 5869) Raw ECDH output is NOT directly used as a key (may be biased, low entropy bits) HKDF-Extract: PRK = HMAC-SHA256(salt, ecdh_output) ← normalize to uniform 256-bit HKDF-Expand: key = HMAC-SHA256(PRK, info || 0x01) ← expand to desired key length TLS 1.3 derives: handshake_traffic_secret, app_traffic_secret, resumption_master_secret Each derivation uses a different “label” string so all keys are independent.

Why not use raw ECDH output directly? The x-coordinate of a curve point has structure: the MSB is often 0 for many curves, and small-subgroup attacks can force the output to a predictable value if the implementation skips cofactor multiplication. HKDF removes all structure by hashing through HMAC, ensuring any 256-bit output is cryptographically uniform and independent of other keys derived from the same ECDH exchange.

🔬 Advanced: X3DH — Signal Protocol Initial Key Agreement

The Extended Triple Diffie-Hellman (X3DH) protocol (Marlinspike & Perrin, 2016) enables asynchronous key agreement — Alice can establish a shared secret with Bob even when Bob is offline. Bob pre-publishes a “key bundle” to a server containing four long-lived and ephemeral public keys.

X3DH Key Agreement (Alice initiates, Bob offline)
Bob publishes: IKB (identity), SPKB (signed prekey), OPKB (one-time prekey)
Alice has: IKA (identity), EKA (ephemeral key, generated fresh)

Alice computes 4 ECDH exchanges:
DH1 = ECDH(IKA, SPKB)   ← Alice identity × Bob signed prekey
DH2 = ECDH(EKA, IKB)   ← Alice ephemeral × Bob identity
DH3 = ECDH(EKA, SPKB) ← Alice ephemeral × Bob signed prekey
DH4 = ECDH(EKA, OPKB) ← Alice ephemeral × Bob one-time prekey

Master Secret = KDF(DH1 ‖ DH2 ‖ DH3 ‖ DH4)
Bob computes the same 4 DH values when he comes online → identical master secret. OPK ensures one-time-pad-like forward secrecy for this session.

X3DH provides: mutual authentication (both identity keys involved), forward secrecy (ephemeral key deleted after), deniability (no certificate-style non-repudiation — either party could have forged the session), and offline initiation. After X3DH, the Double Ratchet Algorithm takes over, deriving a new encryption key for each message independently.

Q1. Why does ECDH achieve 128-bit security with only a 256-bit key, while classic DH needs 3072 bits?
The best attack on ECDLP is Pollard's rho at O(√n) — purely exponential in key size. For n=2^256, that's 2^128 operations. The best DLP attack (Index Calculus) is sub-exponential, requiring a much larger group (3072-bit prime) to achieve the same 2^128 security level.
Q2. Why is raw ECDH output not used directly as an encryption key?
The x-coordinate of the shared EC point has mathematical structure (e.g., leading bits tend toward 0 on some curves) and small-subgroup attacks may force it to predictable values. HKDF-Extract hashes it through HMAC-SHA256, producing a uniformly random PRK with no structure, from which multiple independent keys can be derived with HKDF-Expand.
Q3. In X3DH (Signal Protocol), why is the one-time prekey (OPK) critical for forward secrecy?
The OPK is a single-use ephemeral key Bob uploads in advance. Once used in DH4, the server deletes it. Even if Bob's identity key (IK_B) and signed prekey (SPK_B) are later compromised, DH4 cannot be recomputed — making this session's master secret uniquely forward-secret. Without OPK, all sessions sharing the same 3-key bundle would be retroactively decryptable if those keys were exposed.
  • ECDH: same math as DH but on elliptic curves — 256-bit key vs 3072-bit for equivalent 128-bit security
  • ECDHE (ephemeral): new key pair per session → Perfect Forward Secrecy; mandatory in TLS 1.3
  • HKDF: ECDH output → HMAC-SHA256 → uniform PRK → multiple independent session keys
  • X3DH: 4 ECDH exchanges enable asynchronous key agreement; one-time prekey ensures per-session forward secrecy

2.3 Digital Signatures (RSA, DSA, ECDSA)

Digital Signature
A digital signature provides: Authentication (who sent it?), Integrity (was it modified?), and Non-repudiation (the sender cannot deny sending it). It is created using the sender's private key and verified using their public key.

How RSA Digital Signatures Work

Signing and Verification Process
SIGNING (Alice sends document to Bob): 1. Alice computes hash: h = SHA-256(Document) 2. Alice encrypts hash with her PRIVATE KEY: Sig = hᵈ mod n 3. Alice sends: (Document, Sig) VERIFICATION (Bob receives): 1. Bob computes hash of received document: h1 = SHA-256(Document) 2. Bob decrypts signature with Alice's PUBLIC KEY: h2 = Sigᵉ mod n 3. If h1 == h2: Signature VALID ✓ (document is from Alice, not tampered) If h1 != h2: Signature INVALID ✗ (tampered or wrong sender)
💡
Why hash first? Two reasons: (1) RSA can only encrypt data smaller than the key size (~245 bytes for RSA-2048). You cannot directly sign a 1 GB file. (2) Hashing is fast — SHA-256 hashing a 1 GB file takes milliseconds. RSA signing the 256-bit hash takes microseconds. Direct RSA signing would take hours.

DSA vs ECDSA vs RSA Signatures

FeatureRSA SignatureDSAECDSA
Hard ProblemInteger FactorizationDiscrete LogarithmEC Discrete Logarithm
Can also Encrypt?✅ Yes❌ Sign only❌ Sign only

Nonce RequirementOptional (PSS padding)⚠ Must be random per-sign⚠ Must be random per-sign

⚠️
ECDSA/DSA Nonce Reuse is Fatal. If the same random nonce k is used for two different ECDSA signatures, an attacker can algebraically recover the private key. This exact flaw broke the Sony PlayStation 3 in 2010 (a constant nonce was used for firmware signing). Always use a cryptographically secure random k per signature.
⚡ Extra: EdDSA & Ed25519 — The Modern Standard

EdDSA (Edwards-curve Digital Signature Algorithm) using Ed25519 (Curve25519 in Edwards form) is rapidly replacing ECDSA. Key advantages: deterministic (no random nonce needed — k is derived from the private key and message via a hash), constant-time by design (no side-channel timing leaks), faster than ECDSA, and the signature is always 64 bytes. Used by OpenSSH default keys, Signal protocol, and Ethereum validator signing.

🔬 Advanced: BLS Signatures — Pairing-Based Aggregation

BLS (Boneh-Lynn-Shacham) signatures (2001) are built on bilinear pairings — a cryptographic map e: G1 × G2 → GT between elliptic curve groups. The key property: multiple signatures on different messages from different signers can be aggregated into a single constant-size signature, verifiable in one pairing operation.

BLS Signature Scheme (over pairing-friendly curve, e.g. BLS12-381)
KeyGen: sk = random x; pk = x · G (generator point)
Sign(sk, m): σ = sk · H(m)   where H: {0,1}* → G1
Verify(pk, m, σ): check e(σ, G) == e(H(m), pk)

Aggregation: For n signers with sigs σ1…σn:
σagg = σ1 + σ2 + … + σn (single elliptic curve point!)
Verify: e(σagg, G) == ∏ e(H(mi), pki)
n signatures (each 48 bytes on BLS12-381) reduce to one 48-byte aggregate — saving 47×48 = 2256 bytes for 48 validators.

BLS aggregation is used in Ethereum 2.0 Proof-of-Stake: each block contains thousands of validator attestations. Without BLS, storing all signatures would be prohibitive. With BLS, all attestations for a slot aggregate into a single 96-byte signature. BLS is also used in Chia, Filecoin, and threshold signature schemes where no single party holds the full private key (threshold-t-of-n signing via secret sharing).

Q1. Why is the message hashed before RSA signing, instead of signing the full message?
Two reasons: (1) RSA can only operate on data smaller than the key size (~245 bytes for RSA-2048). A 1 GB document cannot be RSA-signed directly. (2) Hashing is fast (SHA-256 of 1 GB takes milliseconds), while RSA is slow. Sign the 256-bit hash → microseconds per signature regardless of document size.
Q2. How did nonce reuse in ECDSA break the Sony PlayStation 3?
Sony used a constant nonce k for all PS3 firmware ECDSA signatures. From any two signatures (r₁,s₁) and (r₂,s₂) on messages z₁,z₂: since r₁=r₂ (same k), solve: k = (z₁-z₂)/(s₁-s₂) mod q, then d = (s·k - z)/r mod q. The private key d was recovered, allowing anyone to sign arbitrary PS3 firmware as Sony.
Q3. What advantage does Ed25519 (EdDSA) have over ECDSA regarding nonce generation?
Ed25519 is deterministic — the nonce k is derived as k = H(private_key || message), never requiring a random number generator. This eliminates the catastrophic nonce reuse vulnerability entirely. It's also constant-time by design (resistant to timing attacks) and produces 64-byte signatures regardless of message size.
  • Digital signatures provide Authentication, Integrity, and Non-repudiation (AIN)
  • Sign with PRIVATE key; verify with PUBLIC key (opposite of encryption)
  • Hash before signing: RSA size limit (~245 bytes) + performance (SHA-256 is fast)
  • ECDSA/DSA nonce reuse is fatal: two signatures with same k → private key recovery (PS3 hack)
  • Ed25519 (EdDSA): deterministic nonce, constant-time, 64-byte sigs — modern standard replacing ECDSA

2.4 Digital Certificates & X.509

Digital Certificate (X.509)
A digital certificate is an electronic document that binds a public key to an identity, signed by a trusted Certificate Authority (CA). It answers: "I claim to own this public key — here is a trusted third party verifying that claim."

💡
Subject Alternative Names (SANs): Modern browsers ignore the "Common Name" field entirely. They only look at SANs for domain matching. A certificate must list every domain it covers in SANs (e.g., google.com, www.google.com, apis.google.com). Wildcard SANs (*.google.com) cover one subdomain level.

Certificate Revocation: CRL vs OCSP vs OCSP Stapling

When a private key is compromised, the certificate must be invalidated BEFORE it expires:

MethodHow It WorksProblem
CRL
(Certificate Revocation List)		 CA publishes a list of all revoked cert serial numbers. Client downloads the entire list. Lists can grow to gigabytes. Downloaded infrequently (stale). Huge latency on first check.
OCSP
(Online Certificate Status Protocol)		 Client sends a real-time query to CA: "Is cert #XYZ valid?" Gets tiny Good/Revoked response. CA learns which websites you visit (privacy). Adds latency per connection. CA must be always online.
OCSP Stapling Server periodically fetches its own OCSP response from CA and "staples" it to the TLS handshake. Best of both worlds. No client-to-CA communication. Time-stamped CA response proves validity. Standard in modern TLS.
⚡ Extra: Certificate Transparency (CT)

Certificate Transparency is a public, append-only audit log of all certificates ever issued. When a CA issues a certificate, it must submit it to public CT logs. Browsers like Chrome require all TLS certificates to be logged in at least two CT logs. This prevents rogue CAs from issuing unauthorized certificates silently — anyone can query the logs and detect if a certificate was issued for their domain without their knowledge. This caught several CA compromises, including the DigiNotar breach (2011) where attackers issued fraudulent certs for *.google.com.

2.5 Public Key Infrastructure (PKI)

PKI — Public Key Infrastructure
The framework of policies, hardware, software, people, and procedures needed to manage digital certificates and public-key encryption. It creates and maintains a web of trust between entities on the internet.

PKI Components

Chain of Trust Verification

When your browser connects to a website, it receives a certificate chain: End-Entity Cert → Intermediate CA Cert → Root CA Cert. The browser:

  1. Verifies the Root CA cert is in its built-in trust store (browsers and OS ship with ~100-150 trusted root CAs).
  2. Verifies the Intermediate CA cert was signed by the Root CA.
  3. Verifies the End-Entity cert was signed by the Intermediate CA.
  4. Checks the cert's validity dates, domain name, and revocation status.
  5. If all checks pass, the padlock icon appears.
⚠️
Man-in-the-Middle via Fake Certificate: Eve intercepts Alice's DH parameters and sends her own public key. She decrypts Alice's messages, re-encrypts them with Bob's key, and forwards. Neither Alice nor Bob knows. Solution: The server's DH parameters are signed by its RSA/ECDSA certificate, which is verified against a trusted CA chain. Eve cannot forge a signature without the private key.
Q1. TLS 1.3 completes in 1 RTT vs TLS 1.2's 2 RTT. What makes this possible?
TLS 1.3 sends the key_share (ECDHE public key) in the ClientHello itself, so the server can compute the shared secret and start encrypting immediately after ServerHello. TLS 1.2 required a separate negotiation round before exchanging key material. TLS 1.3 also dropped all weak cipher suites, eliminating negotiation overhead.
Q2. What is the risk of TLS 1.3's 0-RTT resumption and how is it mitigated?
0-RTT data is vulnerable to replay attacks — an attacker can re-send recorded 0-RTT packets to trigger the same server-side action again. Mitigation: (1) only use 0-RTT for idempotent requests (GET, not POST/payment). (2) Server tracks seen session ticket nonces in a distributed cache to reject replays. RFC 8446 explicitly warns 0-RTT has "weaker security properties."
Q3. Parse this TLS cipher suite: TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
ECDHE = key exchange via Ephemeral ECDH (provides PFS). RSA = server authentication (server cert is RSA). AES_256_GCM = bulk AEAD encryption using AES-256 in GCM mode (combined encrypt+authenticate). SHA384 = HMAC-SHA384 for key derivation PRF. In TLS 1.3, cipher suites are simplified to just 5 options (e.g., TLS_AES_256_GCM_SHA384) because key exchange and auth are always ECDHE/cert.
  • TLS 1.3: 1-RTT handshake, mandatory ECDHE (PFS), only 5 AEAD cipher suites, removed RC4/MD5/SHA-1/RSA-KeyTransport
  • TLS 1.2: 2-RTT, 300+ cipher suites (many weak), optional PFS
  • mTLS: both client AND server present X.509 certs — used in microservices, Zero Trust architectures
  • Certificate pinning: hardcode expected cert hash in app — prevents MitM even with rogue CA
  • HKDF key schedule: every derived key binds to transcript hash → tampering with handshake immediately produces wrong keys

2.6 SSL / TLS Protocol

TLS (Transport Layer Security)
The successor to SSL. Provides a secure channel over the network (creating HTTPS). Uses asymmetric crypto for authentication/key exchange, symmetric crypto for bulk encryption, and hash functions for integrity. TLS 1.3 is the current standard (2018). TLS 1.0 and 1.1 are deprecated.

TLS 1.3 Handshake (Simplified)

Client ----ClientHello (TLS 1.3, supported cipher suites, key_share: ECDHE public)----> Server Server <---ServerHello (chosen cipher, key_share: Server ECDHE public)---- Server <---Certificate (server X.509 cert)---- Server <---CertificateVerify (signature over handshake using server private key)---- Server <---Finished (HMAC over handshake transcript)---- [Client verifies cert chain, verifies CertificateVerify signature] [Both derive symmetric keys from ECDHE shared secret] Client ----Finished (HMAC)----> Server [Encrypted Application Data flows here -- just 1 RTT!]

⚡ Extra: TLS 0-RTT & Replay Risk

TLS 1.3 supports 0-RTT resumption: a client that has previously connected can send encrypted data on the very first packet, before the handshake completes. This eliminates the latency cost of TLS entirely for repeat visitors. The tradeoff: 0-RTT data is vulnerable to replay attacks. An attacker can re-send recorded 0-RTT data to the server. For this reason, 0-RTT must only be used for idempotent requests (GET, not POST) and servers must implement anti-replay measures (ticket nonce tracking).

⚡ Extra: Mutual TLS (mTLS) & Certificate Pinning

Standard TLS only authenticates the server to the client. Mutual TLS (mTLS) requires the client to also present a certificate, authenticating both ends. The server sends a CertificateRequest message in the handshake; the client responds with its own X.509 certificate signed by a CA the server trusts.

FeatureStandard TLSMutual TLS (mTLS)
Who is authenticated?Server only (via cert)Both server AND client (via certs)
Use CasePublic HTTPS websitesAPI-to-API, microservices, Zero Trust
Client auth methodUsername/password in HTTP layerX.509 certificate at TLS layer
Who issues client cert?N/AInternal PKI or CA managed by the org
Used byEvery HTTPS siteKubernetes, Istio service mesh, AWS API GW

Certificate Pinning: An app hardcodes the expected server certificate (or its public key hash) and refuses any connection that doesn't present that exact cert — even if the cert is signed by a trusted CA. Used by mobile apps (Twitter, Google), prevents MitM even with rogue CA certificates. Downside: updates require app re-release if cert changes. Modern practice: public key pinning (pin the key hash, not the cert) so cert rotation doesn't break pins.

🔬 Advanced: TLS 1.3 Formal Security — OPTLS & Key Schedule

TLS 1.3's security was formally analyzed in the OPTLS framework (Krawczyk & Wee, 2015) and the miTLS project, proving security under the DDH and PRF assumptions. Unlike TLS 1.2 (which required 2 round-trips and had no formal proof), TLS 1.3's handshake is proven secure against key-compromise impersonation, forward secrecy violations, and unknown key-share attacks.

TLS 1.3 Key Schedule (HKDF-based)
Early Secret = HKDF-Extract(0, PSK or 0)
Handshake Secret = HKDF-Extract(ECDHE output, Early Secret derivative)
Master Secret = HKDF-Extract(0, Handshake Secret derivative)

client_handshake_traffic_secret = HKDF-Expand-Label(HS, “c hs traffic”, Hello hash)
server_handshake_traffic_secret = HKDF-Expand-Label(HS, “s hs traffic”, Hello hash)
application_traffic_secret_0 = HKDF-Expand-Label(MS, “c ap traffic”, handshake hash)
Each HKDF derivation binds the new key to the transcript hash — a modification of any handshake message immediately produces incorrect keys on both sides, providing handshake integrity.

0-RTT formal security: The OPTLS analysis shows 0-RTT provides only weak forward secrecy — if the PSK is compromised, past 0-RTT data is revealed. This is an intentional tradeoff: RFC 8446 explicitly labels 0-RTT as “weaker security properties” and mandates server-side anti-replay (session ticket nonce tracking in a distributed cache).

2.7 Perfect Forward Secrecy (PFS)

Perfect Forward Secrecy (PFS)
A property of a key exchange protocol where the compromise of long-term private keys does NOT compromise past session keys. Each session uses a unique ephemeral key that is deleted after the session. Past encrypted traffic remains secure even if the server's certificate private key is later stolen.
Without PFS (Static RSA Key Exchange — old TLS 1.2)
Client encrypts pre-master secret with Server RSA public key. Server decrypts with Server RSA private key. If NSA records ALL traffic for 10 years, then steals Server RSA key: → They can decrypt ALL recorded sessions retroactively. ✗
With PFS (ECDHE — TLS 1.3)
Server generates NEW ECDHE key pair for EVERY connection. Session key derived from ephemeral ECDHE exchange. Ephemeral private key DELETED immediately after handshake. Server RSA cert only signs the ECDHE parameters (authentication). If NSA records traffic, then steals Server RSA key later: → They verify the handshake signatures but cannot decrypt traffic. → The ephemeral ECDHE private keys are gone forever. ✓
🔬 Advanced: Formal PFS & Key-Compromise Impersonation (KCI)

Formally (Günther, 1990 / Bellare-Rogaway model): a protocol provides Perfect Forward Secrecy if the session key of any completed session remains computationally indistinguishable from random even after all long-term private keys are revealed. This requires ephemeral key material that is: (1) freshly generated per session, (2) independent of long-term keys, and (3) securely deleted after use.

PFS vs Key-Compromise Impersonation (KCI)
PFS failure: Long-term key Klt revealed → past sessions decryptable
KCI attack: Adversary with Klt impersonates other party in FUTURE sessions

ECDHE solves PFS: sksession is independent of Klt
TLS 1.3 resists KCI: client Finished = MAC over full transcript → impersonator
  can't forge without client's ephemeral key, even holding server cert key
Why secure deletion matters: OS garbage collectors, swap files, and RAM may retain deleted keys. Secure deletion requires explicit memory zeroing: OPENSSL_cleanse(), SecureZeroMemory(). HSMs never export private keys — strongest PFS guarantee.

2.8 PGP & S/MIME — Secure Email

PGP — Pretty Good Privacy (Phil Zimmermann, 1991)
Standard email ends-to-end encryption. PGP uses a hybrid approach: fast symmetric encryption for the message, slow asymmetric encryption only for the session key. Creates the famous -----BEGIN PGP MESSAGE----- blocks.

How PGP Encrypts a Message

  1. Compress: Message is compressed (reduces size, removes statistical patterns).
  2. Generate Session Key: A random 256-bit AES session key is created.
  3. Encrypt Message: Compressed message encrypted symmetrically with the AES session key.
  4. Encrypt Session Key: The AES session key encrypted with the recipient's RSA public key.
  5. Bundle: (Encrypted Session Key + Encrypted Message) concatenated.
  6. Radix-64 / Base64: Binary bundle encoded to printable ASCII for email transport.

Why use a session key? RSA can only encrypt small amounts of data (<245 bytes for RSA-2048). A 1MB email cannot be RSA-encrypted directly. By encrypting only the tiny 256-bit session key with RSA, and the full message with fast AES, PGP achieves both security and performance.

💡
PGP Trust Levels: Ultimate (your own key), Full (you directly verified this person's key), Marginal (somewhat trusted). A key is considered valid if: signed by you (ultimate), OR signed by 1 fully-trusted person, OR signed by 2+ marginally-trusted people.
⚡ Extra: Signal Protocol — Modern Secure Messaging

The Signal Protocol (used in WhatsApp, Signal, Facebook Messenger) solves PGP's key management complexity. It uses X3DH (Extended Triple Diffie-Hellman) for initial key agreement and the Double Ratchet Algorithm for forward secrecy in each message. The Double Ratchet combines a Diffie-Hellman ratchet (new key pair every few messages) with a symmetric-key ratchet (KDF chain). This provides both forward secrecy (past messages safe if key compromised) and break-in recovery (future messages safe after an attacker loses access).

2.9 Practice MCQs — Unit 2 (22 Questions)

Difficulty: 🌺 Easy  |  🍡 Medium  |  🔴 Hard  |  💀 Expert

Q1. In Diffie-Hellman, Alice sends A = gᵃ mod p. What does Eve need to find the shared secret?
(b) Eve knows p, g, A, and B (all public). To compute the shared secret S = gᵃᵇ mod p, she needs either a or b. Finding a from A = gᵃ mod p is the DLP — computationally infeasible for large p.
Q2. A digital signature uses the sender's private key to sign and the recipient uses what to verify?
(c) Sender's public key. The sender signs with their PRIVATE key. Anyone with the sender's PUBLIC key can verify. This is the reverse of encryption (where recipient's PUBLIC key encrypts, PRIVATE key decrypts).
Q3. The "E" in ECDHE stands for:
(c) Ephemeral. A new key pair is generated for every TLS session and discarded after. This provides Perfect Forward Secrecy — past sessions remain secure even if the long-term certificate private key is later compromised.
Q4. Which certificate revocation mechanism allows the web server itself to provide fresh revocation status during the TLS handshake?
(c) OCSP Stapling. The server fetches a signed, time-stamped OCSP response from the CA and staples it to the TLS handshake. No client-to-CA query needed, solving both the latency and privacy issues of plain OCSP.
Q5. In PGP, why is a random session key generated for each message?
(a) RSA can only directly encrypt ~245 bytes (for RSA-2048). A full email cannot be RSA-encrypted. PGP generates a random AES session key, encrypts the message with fast AES, and only encrypts the small session key with RSA. This hybrid approach gives RSA's key-distribution benefits with AES's speed.
Q6. What does the Root CA certificate use to prove its own authenticity?
(b) Self-signed, pre-installed. Root CA certs are self-signed (they sign themselves). Their trustworthiness comes from being pre-installed in browser and OS trust stores — a manual, curated process by browser vendors and OS makers. There is no higher authority above root CAs.
Q7. TLS 1.3 mandates which property for all key exchanges?
(b) Perfect Forward Secrecy via ECDHE. TLS 1.3 completely removed static RSA key transport. All key exchanges use ephemeral ECDHE. This means PFS is mandatory for all TLS 1.3 connections.
Q8. The ECDSA PlayStation 3 hack demonstrated which critical vulnerability?
(b) Nonce reuse. Sony used a constant nonce k for all PS3 firmware ECDSA signatures. From two signatures using the same k, attackers computed: k = (z1-z2)/(s1-s2) and then the private key d = (s·k - z)/r. All PS3 firmwares were now signable by anyone.
Q9. In PKI, what is the role of the Registration Authority (RA)?
(b) The RA handles identity verification (e.g., checking domain control for DV certs, or legal documentation for EV certs). Once verification is complete, the RA instructs the CA to issue the certificate. The CA focuses only on signing.
Q10. What is the key advantage of PGP's "Web of Trust" over PKI?
(b) Decentralized. PKI requires trusting commercial CAs. If a CA is compromised (like DigiNotar in 2011), all its certs become suspect. PGP's Web of Trust distributes trust — you trust people you know personally, building a network without any single point of failure.
Q11. Which X.509 v3 extension field do modern browsers use to match a certificate to a domain name?
(c) Subject Alternative Name (SAN). Modern browsers (Chrome since 2017, all others now) ignore the CN field for domain validation entirely. Only the SAN extension is checked. A single cert can cover multiple domains via multiple SAN entries.
Q12. What does "Radix-64" encoding in PGP solve?
(b) Email (SMTP) was originally designed for 7-bit ASCII text. Binary data (ciphertext) cannot pass through email servers unchanged. Radix-64 (Base64 + CRC checksum) converts binary to printable ASCII, producing the -----BEGIN PGP MESSAGE----- block that survives email transport.
🍡 MediumQ13. Why must raw ECDH shared output be processed through HKDF before use as an encryption key?
(b) Structural bias and low-entropy bits. The raw ECDH output (x-coordinate of the shared curve point) has mathematical structure: the MSB is often 0, and small-subgroup attacks may force predictable values. HKDF-Extract (an HMAC-based hash) removes all structure, producing a uniformly random PRK. HKDF-Expand then derives multiple independent keys (handshake key, traffic key, resumption key) from a single ECDH exchange with different labels.
🔴 HardQ14. In the DDH (Decisional Diffie-Hellman) assumption, an adversary must distinguish between which two distributions?
(b) DDH asks: is the third element the real DH output gab, or a random gc? If an adversary can distinguish these with non-negligible probability, DDH is broken. DDH being hard means the DH shared secret looks like a random group element — this is why DH provides semantic security for protocols built on it (like ElGamal). Note: DDH is believed true over prime-order EC groups but is FALSE over Zp* with smooth p−1.
🔴 HardQ15. In X3DH (Signal Protocol), why is the one-time prekey (OPK) included in addition to the identity and signed prekeys?
(c) One-time forward secrecy. The OPK is a single-use ephemeral key uploaded by Bob in advance. Once Alice uses it in DH4, the server deletes it. Even if Bob's identity key and signed prekey are later compromised, DH4 (which used the OPK) cannot be recomputed — making this session's master secret uniquely forward secret. Without OPK, multiple sessions could share the same 3-key bundle, enabling retrospective decryption if those keys are later exposed.
💀 ExpertQ16. BLS signature aggregation uses a bilinear pairing e: G1×G2→GT. When verifying an aggregate signature σagg = σ1+…+σn, which equation must hold?
(b) e(σagg, G) = ∏i e(H(mi), pki). By bilinearity: e(σagg, G) = e(∑σi, G) = ∏ e(σi, G) = ∏ e(ski·H(mi), G) = ∏ e(H(mi), ski·G) = ∏ e(H(mi), pki). This single pairing equation verifies ALL n signatures simultaneously, enabling Ethereum 2.0 to aggregate thousands of validator attestations into one 96-byte signature.
🍡 MediumQ17. In Mutual TLS (mTLS), what is the key difference from standard TLS that makes it suitable for microservice authentication?
(b) Client certificate authentication at the transport layer. Standard TLS only authenticates the server; the client is authenticated at the application layer (passwords, tokens). mTLS authenticates both sides via X.509 certs during the TLS handshake — before any application data is exchanged. This makes it ideal for microservice-to-microservice authentication in Zero Trust architectures (Kubernetes, Istio) where every service must prove its identity at every connection.
🔴 HardQ18. In TLS 1.3's HKDF key schedule, modifying any single byte of the ClientHello message causes which effect?
(b) All derived keys diverge. TLS 1.3's HKDF-Expand-Label derivations include the running transcript hash as input. A modified ClientHello produces a different transcript hash, which propagates into every HKDF derivation: handshake_traffic_secret, server_handshake_traffic_secret, and all application_traffic_secrets become different on client and server. The Finished MAC (which commits to the full transcript) will then fail verification — providing cryptographic binding of all keys to the exact transcript, preventing handshake tampering.
🍡 MediumQ19. Why does TLS 1.3 reduce the number of cipher suites from 300+ (TLS 1.2) to just 5?
(b) TLS 1.3 decoupled key exchange (always ECDHE) and authentication (always cert-based) from the cipher suite. Cipher suites now specify ONLY the AEAD bulk cipher + HKDF hash. All 5 suites are AEAD (authenticated encryption), eliminating the CBC padding oracle and stream cipher vulnerabilities that plagued TLS 1.2's 300+ suite zoo.
🔴 HardQ20. In X3DH, Alice computes 4 ECDH values (DH1–DH4). Which specifically binds Bob's long-term identity to Alice's ephemeral key?
(b) DH2 = ECDH(EK_A, IK_B). This exchange between Alice's ephemeral key and Bob's long-term identity key cryptographically binds the session to Bob's identity — ensuring only someone with IK_B's private key could have participated. DH1 binds Alice's identity to Bob's prekey, DH3 provides ephemeral-to-prekey linkage, and DH4 provides one-time forward secrecy. All four together provide mutual authentication and forward secrecy simultaneously.
🍡 MediumQ21. PGP's "Web of Trust" faces a key weakness compared to PKI. What is it?
(b) Unreliable revocation. In PKI, OCSP/CRL revocation is standardized and clients check it actively. In PGP's Web of Trust, revocation certificates must be manually uploaded to keyservers, which do not automatically notify users holding the old key. A compromised PGP private key may remain "trusted" in other users' keyrings for years. This is one reason PGP adoption failed outside niche communities despite its cryptographic strength.
💀 ExpertQ22. Certificate Transparency (CT) prevents which specific attack that OCSP and CRL cannot?
(b) Silent fraudulent certificate issuance. OCSP/CRL only tell you if a KNOWN certificate is revoked — they cannot detect a certificate you don't know exists. CT logs are public and append-only: every issued certificate must be submitted. Domain owners can monitor CT logs for unauthorized certs. This caught the DigiNotar breach (2011) and Symantec mis-issuances (2015–2017), leading to Chrome distrusting Symantec entirely in 2018.
