P.1 Practical: DES Subkey Generation

💻 Practical 1  •  Theory: Unit 1 §1.6 DES

Learning Objectives

  • Understand how DES generates 16 subkeys from a 64-bit master key
  • See the PC-1 and PC-2 permutations in action
  • Verify each subkey is 48 bits derived from 56 effective key bits

Code Walkthrough (from your des.py)

Python — DES Key Schedule Core Logic

# PC-1: 64-bit key -> 56-bit key (drops parity bits at positions 8,16,24,32,40,48,56,64)
PC1 = [57,49,41,33,25,17,9, 1,58,50,42,34,26,18,
       10, 2,59,51,43,35,27,19,11, 3,60,52,44,36,
       63,55,47,39,31,23,15, 7,62,54,46,38,30,22,
       14, 6,61,53,45,37,29,21,13, 5,28,20,12, 4]

# Shift schedule per round: 1 or 2 positions
SHIFT_SCHEDULE = [1,1,2,2,2,2,2,2,1,2,2,2,2,2,2,1]

def generate_subkeys(key_hex):
    key_bin = bin(int(key_hex, 16))[2:].zfill(64)  # hex -> 64-bit binary
    key_56  = ''.join(key_bin[p-1] for p in PC1)   # apply PC-1

    C, D = key_56[:28], key_56[28:]                 # split into C and D halves
    subkeys = []

    for i in range(16):
        # Left circular shift
        n = SHIFT_SCHEDULE[i]
        C = C[n:] + C[:n]
        D = D[n:] + D[:n]
        # Apply PC-2 to get 48-bit subkey
        CD = C + D
        K  = ''.join(CD[p-1] for p in PC2)
        subkeys.append(K)
        print(f"Round {i+1:2d}: K = {hex(int(K,2)).upper()}")

    return subkeys

# Run with standard test key
generate_subkeys("133457799BBCDFF1")

💡
Exam question type: “How many bits are in each DES round subkey, and how is it derived?” — 48 bits. Derived by: (1) stripping 8 parity bits from 64-bit key via PC-1 = 56 bits, (2) splitting into C,D (28 bits each), (3) circular shift per round, (4) PC-2 selects 48 of 56 bits.

def compute_file_hash(filepath):
    sha256 = hashlib.sha256()
    with open(filepath, 'rb') as f:
        for chunk in iter(lambda: f.read(4096), b''):
            sha256.update(chunk)
    return sha256.hexdigest()

Analysis Questions

  1. Why do both MD5 and SHA-256 show complete hash differences despite only one character changing? (Avalanche Effect — diffusion ensures every output bit depends on every input bit)
  2. Why is MD5 still acceptable for file integrity checks (not passwords)? (MD5 collision resistance is broken, but pre-image resistance is still intact — an attacker cannot find a file that matches a given MD5 hash easily)
  3. Why is SHA-256 preferred? (collision resistance: 2¹²&sup8;, vs MD5's broken 2&sup6;&sup4;; and NIST-approved)

P.3 Practical: ECC Diffie-Hellman Key Exchange

Python — ECDH Key Exchange Step-by-Step (from your ecc_step.py)
from cryptography.hazmat.primitives.asymmetric import ec
from cryptography.hazmat.backends import default_backend

# === ALICE ===
# Step 1: Generate Alice's ephemeral ECC key pair (private + public)
alice_private = ec.generate_private_key(ec.SECP256R1(), default_backend())
alice_public  = alice_private.public_key()

# === BOB ===
# Step 2: Generate Bob's ephemeral ECC key pair
bob_private = ec.generate_private_key(ec.SECP256R1(), default_backend())
bob_public  = bob_private.public_key()

print("Alice's public key:", alice_public.public_bytes(...).hex()[:40], "...")
print("Bob's public key:",   bob_public.public_bytes(...).hex()[:40], "...")

# === EXCHANGE PUBLIC KEYS (over public channel) ===

# === DERIVE SHARED SECRET ===
# Alice computes: a * B = a * (b * G) = ab * G
alice_shared = alice_private.exchange(ec.ECDH(), bob_public)

# Bob computes: b * A = b * (a * G) = ab * G
bob_shared   = bob_private.exchange(ec.ECDH(), alice_public)

print("
Alice's shared secret:", alice_shared.hex())
print("Bob's shared secret:  ", bob_shared.hex())
print("Secrets match:", alice_shared == bob_shared)

# Derive symmetric key from shared secret using HKDF
from cryptography.hazmat.primitives.kdf.hkdf import HKDF
from cryptography.hazmat.primitives import hashes

aes_key = HKDF(
    algorithm=hashes.SHA256(), length=32,
    salt=None, info=b'ecdh-aes-key'
).derive(alice_shared)
print("Derived AES-256 key:", aes_key.hex())

Why HKDF?

The raw ECDH shared secret is a point on the elliptic curve — it is not uniformly random. HKDF (HMAC-based Key Derivation Function) extracts entropy from it and “stretches” it into a properly random AES key. It also allows deriving multiple keys (encryption + MAC) from a single shared secret by varying the info parameter.

P.4 Practical: ECC Secure Communication

💻 Practical 4  •  Theory: Unit 1 §1.8 AES | Unit 1 §1.10 ECC

This builds on P.3: After Alice and Bob derive a shared AES key via ECDH, they use it to encrypt/decrypt actual messages with AES-GCM (Authenticated Encryption).

Python — Full ECC Secure Communication (from ecc_secure_communication.py)
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
import os

# [Assuming alice_shared derived from ECDH as in P.3]
aes_key = HKDF(...).derive(alice_shared)  # 32-byte AES-256 key

# === ALICE ENCRYPTS ===
message = b"Hello Bob! This is a secret from Alice."
nonce   = os.urandom(12)   # 96-bit random nonce (MUST be unique per message)

cipher  = AESGCM(aes_key)
ciphertext = cipher.encrypt(nonce, message, associated_data=b"Alice->Bob")
#                                           ^ AAD: authenticated but not encrypted

print("Ciphertext (hex):", ciphertext.hex())
print("Nonce:", nonce.hex())
print("Tag included in ciphertext (last 16 bytes):", ciphertext[-16:].hex())

# === BOB DECRYPTS ===
# Bob has same aes_key from his ECDH computation
cipher2  = AESGCM(aes_key)
plaintext = cipher2.decrypt(nonce, ciphertext, associated_data=b"Alice->Bob")
print("
Bob received:", plaintext.decode())

# If Eve modifies even 1 bit of ciphertext:
tampered = ciphertext[:-1] + bytes([ciphertext[-1] ^ 0x01])
try:
    cipher2.decrypt(nonce, tampered, associated_data=b"Alice->Bob")
except Exception as e:
    print("Tampered message rejected:", e)  # AESGCM raises InvalidTag
Ciphertext (hex): 7a3b8c2d1e9f4a6b5c8d3e2f1a0b9c8d7e6f... Nonce: 4f8a2b7c1d9e3f5a Tag (last 16 bytes): 9e3f5a8b2c7d1e4f6a9b3c8d2e7f1a4b Bob received: Hello Bob! This is a secret from Alice. Tampered message rejected: Authentication tag mismatch

Key Points

  • AES-GCM provides both encryption (CTR mode) and authentication (GHASH — a Galois field MAC). If ANY bit of the ciphertext is changed, decryption raises InvalidTag.
  • Nonce must NEVER repeat with the same key. A repeated nonce in GCM allows an attacker to XOR ciphertexts and recover plaintext, and also to forge valid authentication tags.
  • Associated Data (AAD) is authenticated but not encrypted. Useful for routing headers (who is it from/to) that cannot be hidden but must not be tampered with.

P.5 Practical: RSA & AES with PyCryptodome

💻 Practical 5  •  Theory: Unit 1 §1.9 RSA | Unit 1 §1.8 AES

Using the PyCryptodome library (from your cryptoassignment.py) to implement hybrid RSA+AES encryption:

Python — Hybrid RSA+AES Encryption (PyCryptodome)
from Crypto.PublicKey import RSA
from Crypto.Cipher import AES, PKCS1_OAEP
from Crypto.Random import get_random_bytes

# === KEYGEN ===
# Generate RSA-2048 key pair
rsa_key    = RSA.generate(2048)
public_key = rsa_key.publickey()

# === ENCRYPT (Hybrid) ===
message = b"Sensitive data: account balance $1,337,000"

# 1. Generate random 256-bit AES session key
session_key = get_random_bytes(32)

# 2. Encrypt AES session key with RSA-OAEP
rsa_cipher  = PKCS1_OAEP.new(public_key)
enc_session_key = rsa_cipher.encrypt(session_key)

# 3. Encrypt actual message with AES-EAX (authenticated)
aes_cipher = AES.new(session_key, AES.MODE_EAX)
ciphertext, tag = aes_cipher.encrypt_and_digest(message)

print("Encrypted session key:", enc_session_key.hex()[:40], "...")
print("AES ciphertext:", ciphertext.hex())
print("AES auth tag:", tag.hex())

# === DECRYPT ===
# 1. Recover AES session key using RSA private key
rsa_decipher  = PKCS1_OAEP.new(rsa_key)
dec_session_key = rsa_decipher.decrypt(enc_session_key)

# 2. Decrypt AES ciphertext
aes_decipher = AES.new(dec_session_key, AES.MODE_EAX, nonce=aes_cipher.nonce)
plaintext = aes_decipher.decrypt_and_verify(ciphertext, tag)
print("Decrypted:", plaintext.decode())
Encrypted session key: 4f8a2b7c1d9e3f5a8b2c7d1e4f6a9b3c... (256 bytes) AES ciphertext: 7e3b8c2d1f9a4b6c5d8e3f2a1b0c9d8e7f6a (42 bytes) AES auth tag: 9e3f5a8b2c7d1e4f6a9b3c8d2e7f1a4b (16 bytes) Decrypted: Sensitive data: account balance $1,337,000
💡
Why PKCS1_OAEP and not plain RSA? Plain RSA (textbook) is deterministic and malleable. OAEP adds randomized padding that makes RSA non-deterministic (same plaintext encrypts to different ciphertext each time) and resistant to chosen-ciphertext attacks like Bleichenbacher's. Always use OAEP in production.

P.6 Practical: PKI Setup with OpenSSL

💻 Practical 6  •  Theory: Unit 2 §2.5 PKI | Unit 2 §2.4 Certificates

Build a complete 3-tier PKI: Root CA → Intermediate CA → Server Certificate

Shell — Step 1: Create Root CA
# Generate Root CA private key (RSA 4096)
openssl genrsa -aes256 -out root-ca.key 4096

# Self-sign the Root CA certificate (valid 10 years)
openssl req -x509 -new -nodes -key root-ca.key -sha256 \
  -days 3650 -out root-ca.crt \
  -subj "/C=IN/O=MyOrg Root CA/CN=MyOrg Root CA"

# Verify the root certificate
openssl x509 -in root-ca.crt -text -noout | head -20
Shell — Step 2: Create Server Certificate
# Generate server private key
openssl genrsa -out server.key 2048

# Create Certificate Signing Request (CSR)
openssl req -new -key server.key -out server.csr \
  -subj "/C=IN/O=MyOrg/CN=www.myorg.com"

# Add Subject Alternative Names extension
cat > san.ext << EOF
[SAN]
subjectAltName=DNS:www.myorg.com,DNS:myorg.com,IP:192.168.1.10
EOF

# Sign server CSR with Root CA
openssl x509 -req -in server.csr -CA root-ca.crt -CAkey root-ca.key \
  -CAcreateserial -out server.crt -days 365 -sha256 \
  -extfile san.ext -extensions SAN

# Verify chain
openssl verify -CAfile root-ca.crt server.crt
# Expected: server.crt: OK

CS.1 Case Study: Orion Technologies — Known-Plaintext Attack

📋 Scenario: Orion Technologies uses an aging single-DES encrypted channel to transmit daily financial reports between their Singapore and London offices. An attacker (rival firm) has been passively capturing ciphertext for weeks. They also have access to a financial report template that all reports use as a header.

Attack Analysis

  1. Attack Type: Known-Plaintext Attack (KPA) — The attacker has the standard report header format (plaintext) and its corresponding encrypted version (ciphertext).
  2. Why DES is vulnerable: 56-bit key = 2⁵⁶ = ~72 quadrillion keys. A modern GPU cluster can test billions of keys per second. At 1 billion keys/second: 72,000 seconds = ~20 hours. Cloud computing: ~$50 in cloud credits.
  3. KPA + Brute Force: For each candidate key, encrypt the known plaintext. If the output matches the known ciphertext, the key is found. With a known (P, C) pair, this is parallelizable across GPUs.

Exploit Sequence

StepAttacker ActionTechnical Detail
1Passive capture of encrypted trafficPCAP of all ciphertext traffic over 3 weeks
2Identify known plaintextReport header: "FINANCIAL REPORT — ORION TECH — DATE: " (32 bytes)
3Launch KPA brute-forceTest all 2⁵⁶ keys: DES-encrypt header, compare to ciphertext
4Key recoveredKey found in ~18 hours on GPU cluster
5Decrypt all stored traffic3 weeks of financial reports now readable

Recommended Remediation

  • Immediate: Replace DES with AES-256-GCM. 2²⁵⁶ key space is unbreakable. AEAD provides integrity.
  • Short-term: Deploy TLS 1.3 with ECDHE for channel encryption (PFS prevents future decryption of recorded traffic).
  • Structural: Never use static encryption keys for extended periods. Implement key rotation every 30 days.
  • Detection: Monitor for large-scale passive traffic capture (unusual volumes of one-directional traffic without SYN/ACK patterns).

CS.2 Case Study: SecurePay Financial — Multi-Stage Attack

📋 Scenario: SecurePay Financial is a digital payment processor. A sophisticated attacker targets them with a multi-stage campaign: (1) exploit a legacy RSA-512 certificate still in use by a subsidiary, (2) use the compromised identity for a MitM attack, (3) intercept payment session keys.

Stage 1: RSA-512 Factorization

The attacker identifies a subsidiary still using RSA-512 (512-bit key). Using the Number Field Sieve algorithm on a cloud cluster, RSA-512 can be factored in ~1 week for ~$1,000. This recovers the subsidiary's private key.

Why RSA-512 is trivially broken
RSA-512 security level: ~80-bit equivalent Modern NFS factoring: can factor 512-bit number in days Public record: RSA-512 challenge factored in 1999 (on academic hardware) RSA-2048 minimum requirement: 2²⁰⁰ security, not factored by any known method

Stage 2: Certificate Impersonation & MitM

With the private key, the attacker crafts a fake response from the subsidiary's payment gateway, intercepting customer payments. Because they can forge signatures, the TLS handshake verification passes for clients that trust the subsidiary's certificate.

Stage 3: Session Key Interception

Since TLS 1.2 was configured without PFS (static RSA key exchange), the attacker had previously recorded encrypted traffic. With the RSA private key, they now retroactively decrypt all stored TLS pre-master secrets, recovering all payment session data.

⚠️
Root Cause: (1) RSA-512 key (obsolete). (2) No PFS (TLS without ECDHE). (3) No certificate transparency monitoring. (4) No subsidiary security audit.

Step 2: Nonce Reuse — The Fatal Flaw (PS3 Demo)

⚠️
Educational Only: The following demonstrates the nonce-reuse vulnerability that broke Sony's PS3 firmware signing. Never use fixed nonces in production.
How Nonce Reuse Exposes the Private Key
import hashlib, secrets # Simulate ECDSA math over secp256k1 parameters (simplified) # Real PS3 attack: Sony used k = constant for ALL firmware signatures # If k is reused for two signatures on messages m1, m2: # s1 = k^-1 * (z1 + r*d) mod n # s2 = k^-1 * (z2 + r*d) mod n # Same k → same r (r = (k*G).x mod n) # From s1 - s2 = k^-1 * (z1 - z2) → k = (z1 - z2) * (s1 - s2)^-1 mod n # Then d = (s1*k - z1) * r^-1 mod n ← PRIVATE KEY RECOVERED! # Demonstration with toy values: def modinv(a, n): """Extended Euclidean: returns a^-1 mod n""" g, x, _ = extended_gcd(a % n, n) return x % n if g == 1 else None def extended_gcd(a, b): if a == 0: return b, 0, 1 g, x, y = extended_gcd(b % a, a) return g, y - (b // a) * x, x # Toy ECDSA parameters (NOT real curve — demonstration only) n = 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141 k = 42 # FIXED NONCE — Sony's mistake r = pow(k, 2, n) # simplified r (real: (k*G).x) d = secrets.randbelow(n) # victim's private key z1 = int(hashlib.sha256(b"Firmware v1.0").hexdigest(), 16) % n z2 = int(hashlib.sha256(b"Firmware v2.0").hexdigest(), 16) % n s1 = (modinv(k, n) * (z1 + r * d)) % n s2 = (modinv(k, n) * (z2 + r * d)) % n # ATTACK: recover k from two signatures with same r k_recovered = ((z1 - z2) * modinv(s1 - s2, n)) % n d_recovered = (modinv(r, n) * (s1 * k_recovered - z1)) % n print(f"Original private key: {d:#x}") print(f"Recovered private key: {d_recovered:#x}") print(f"Match: {d == d_recovered} ← Sony's PS3 was broken this way")
Q1. After running this code, the tampered message is rejected. Why does changing even one character invalidate the signature?
SHA-256 is used before signing. Any change to the message produces a completely different hash (avalanche effect). The signature verifies by checking: hash(received_message) == RSA-decrypt(signature). Different message → different hash → mismatch → invalid.
Q2. In the PS3 demo, how is k_recovered computed from two signatures (r,s1) and (r,s2)?
Same nonce k → same r in both signatures. From ECDSA equations: s1-s2 = k^-1(z1-z2). Therefore k = (z1-z2) × (s1-s2)^-1 mod n. Then d = (s1×k - z1) × r^-1 mod n. The private key d is algebraically exposed once k is known.

P.9 — AES-CBC Padding Oracle Attack (Python)

📚 Prerequisites
Unit 3 Section 3.3 (Advanced Attacks — Padding Oracles). Install: pip install pycryptodome

Objective: Simulate a CBC padding oracle attack to decrypt a ciphertext without knowing the AES key. This is the vulnerability class behind BEAST (TLS 1.0), POODLE (SSLv3), and Lucky13.

How a Padding Oracle Works

AES-CBC decrypts each block as: P[i] = AES_decrypt(C[i]) ⊕ C[i-1]. Valid PKCS#7 padding ends in 01, 02 02, 03 03 03, etc. A "padding oracle" is any system that tells you differently whether padding was valid — even just different error messages or timing.

Padding Oracle Attack — Decrypt 1 Byte Without the Key
from Crypto.Cipher import AES from Crypto.Util.Padding import pad, unpad import os # ─── SERVER SIDE (victim with "padding oracle") ─────────────────────────── SECRET_KEY = os.urandom(16) # 128-bit AES key — attacker does NOT know this def encrypt(plaintext: bytes) -> tuple[bytes, bytes]: """Server encrypts a message. Returns (iv, ciphertext).""" cipher = AES.new(SECRET_KEY, AES.MODE_CBC) return cipher.iv, cipher.encrypt(pad(plaintext, 16)) def padding_oracle(iv: bytes, ciphertext: bytes) -> bool: """ SERVER ORACLE: decrypts and checks if padding is valid. Returns True if valid padding, False otherwise. THIS is the information leak — even just timing differences count! """ try: cipher = AES.new(SECRET_KEY, AES.MODE_CBC, iv=iv) unpad(cipher.decrypt(ciphertext), 16) return True except ValueError: return False # ─── ATTACKER SIDE ──────────────────────────────────────────────────────── message = b"ATTACK AT DAWN!!" # 16 bytes = 1 AES block (no padding needed) iv, ciphertext = encrypt(message) print(f"[+] Intercepted IV: {iv.hex()}") print(f"[+] Intercepted Ciphertext: {ciphertext.hex()}") print(f"[*] Attacker does NOT know key: {SECRET_KEY.hex()}") print() # Attack: recover plaintext byte-by-byte using padding oracle # For last byte of block: # AES_decrypt(C)[15] ⊕ IV[15] = P[15] # We want valid padding : AES_decrypt(C)[15] ⊕ IV'[15] = 0x01 # So: AES_decrypt(C)[15] = 0x01 ⊕ IV'[15] # And: P[15] = AES_decrypt(C)[15] ⊕ IV[15] recovered = bytearray(16) # Only recovering last byte for this demo (full attack loops over all 16) for guess in range(256): iv_mod = bytearray(iv) iv_mod[15] = guess # modify last IV byte if padding_oracle(bytes(iv_mod), ciphertext): # Valid padding  means: AES_decrypt(C)[15] ⊕ guess = 0x01 intermediate = guess ^ 0x01 plaintext_byte = intermediate ^ iv[15] recovered[15] = plaintext_byte print(f"[+] Last byte recovered: {chr(plaintext_byte)!r} (0x{plaintext_byte:02x})") print(f"[+] Actual last byte: {chr(message[15])!r} (0x{message[15]:02x})") break print() print("[*] Defense: Use AES-GCM (AEAD) instead of AES-CBC.") print("[*] AES-GCM authenticates BEFORE decrypting — no padding oracle possible.")
💡
Why AEAD Eliminates This: AES-GCM computes a GHASH authentication tag over the ciphertext. Decryption verifies the tag FIRST — if it fails, decryption never starts and the padding is never checked. The oracle disappears entirely. This is why TLS 1.3 mandates AEAD-only cipher suites.
Q1. In CBC padding oracle: what information does the oracle leak, and why is even timing difference sufficient?
The oracle leaks whether PKCS#7 padding is valid. Even different response TIMES (Lucky13 attack) are sufficient — the decryption path for valid vs invalid padding takes different CPU cycles. With enough queries (~128 per byte × 16 bytes = ~2048 queries per AES block), the full plaintext is recovered without the key.
Q2. Why doesn't AES-GCM have a padding oracle vulnerability?
AES-GCM is a stream cipher mode — it uses AES in counter (CTR) mode, which produces a keystream XORed with plaintext. There is no padding at all. Additionally, the GHASH authentication tag is verified before any plaintext is returned — decryption is authenticate-then-decrypt, making the padding oracle impossible.
